# rag-embedding-probe 维度实测证据（2026-09-27，真接口）

**为什么有这一份**：spec 的判据「档位**通过 = `200` 且返回宽度 == 所求**」与 DashScope 自己的报错文案**相反**——那条 400 声称允许
`[256, 512, 768, 1024, 1536, 2048, 2560]`，而其中三个值实测会被**静默钳回 1024**。整条判据只有这一份物证，故按本线惯例留档。

**怎么做的**：`probe_dimensions_live.py` **直发原始 HTTP**（本仓代码一行都不在链路里；key 从 gitignore 的 `.env` 取、从不打印），
对 DashScope 原生嵌入端点打同一段请求体、只换 `parameters.dimension`；对照轮**同 key、同端点、只换模型**。
原始输出：`results.txt`。复跑：

```
backend/.venv/Scripts/python.exe pr-build/rag-embedding-probe-2026-09-27/probe_dimensions_live.py
```

## 结果

| 模型 | `dimension` | 状态 | 返回宽度 |
| --- | --- | --- | --- |
| qwen3.7-text-embedding-flash | 不带参数 | 200 | **1024**（＝它的原生宽度） |
| qwen3.7-text-embedding-flash | 256 / 512 / 768 / 1024 | 200 | ＝所求 ✓ |
| qwen3.7-text-embedding-flash | **1536 / 2048 / 2560** | **200** | **1024**（被钳）⚠️ |
| qwen3.7-text-embedding-flash | 128 / 333 / 3072 | 400 `InvalidParameter` | — |
| qwen3.7-text-embedding（对照） | 1536 / 2048 | 200 | 1536 / 2048 ✓ |
| text-embedding-v4（对照） | 1536 / 2048 | 200 | 1536 / 2048 ✓ |

## 结论（写回 spec §3.1 / §3 判据）

1. 该模型**原生 1024**、`333` 被 400 ⇒ 分类为 **①档位型**，真档位集 = {256, 512, 768, 1024}。
2. **200 会撒谎**：1536/2048/2560 被接受却返回 1024 ⇒ 判"通过"必须 **宽度相等**，只看状态码会把这三个值列成可用档。
3. 对照证明**钳位是该模型自己的上限**（非端点、非账号、非环境）：同 key 同端点换模型就如实返回。
4. 400 的文案**不可作为档位清单**（它与实测矛盾），只能靠逐值实测。
